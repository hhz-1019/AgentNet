# 响应慢与卡顿诊断（2026-10-15）

> 后续约束更新：用户要求保留所有前端展示，尤其开场动画。因此本轮最终发布已撤回下文实验中的开场加速和页面懒加载；原始动画、资源等待、组件展示与样式保持不变。下文5.26→2.61秒等数据是已撤回方案的历史对照，不代表最终发布效果。最终范围包括摘要查询、在途GET复用、减少后台重复读取、索引、媒体原始字节读取、连接池预算与内部指标、Server-Timing及静态缓存。上线结果另见 VERIFICATION.md。

结论：目前证据最强的是跨境连接及资源传输波动，叠加前端开场阻塞。后台重复刷新和过量读取进一步增加请求；评论缺索引是数据增长后的隐患。最近一小时云端监控未显示 CPU、内存耗尽，不能把问题简单归因于服务器配置低。

本次只在本地优化和验证，没有执行提交、推送、部署或生产数据库修改。工作期间另一会话把工作区 HEAD 从 `ac2a0af` 更新为 `d7c236d`，涉及招聘入口；保留了这些改动。以下构建数字是整个工作区的前后结果，包含同期招聘页调整，不能将全部体积差额都归因于性能修改。

## 观测方法与边界

- 当前 Windows 网络访问 `https://agentnet.zeabur.app`，读取公开页面、未登录会话及公开动态；每个 curl 路径取 3 个样本，没有做生产压测。
- Chromium 分别以 1440×900 桌面、390×844 手机尺寸新上下文访问；手机尺寸不是实体手机。捕获导航连接、资源下载、主线程长任务、解除开场遮挡时间及截图；未使用私人账号，也未执行生产写操作。
- Zeabur 只读查询确认项目地区为美国洛杉矶，区域名称为 Aliyun California 4C 8GB。读取截至约北京时间 16:01 的最近一小时、每服务 61 个 CPU/内存监控点。
- 本地以生产构建、固定 400ms 的合成 API 响应作对照。测量的是动态页出现且解除 `inert` 的时间，不是 INP，也不是线上 P95。桌面首次 Canvas 绘制在本机仍出现约 1.4～1.6 秒长任务，手机尺寸的第二个上下文未出现同样长任务；不能将其直接解释为所有终端的表现。
- 原始结果保存在忽略提交的 `.agentnet-audit/performance-20261015/`，包括 `live.json`、`before-repeat.json`、`after.json`、`cloud-metrics.json`、测试日志及截图。

## 已确认的问题

| 问题 | 证据 | 影响与处理 |
|---|---|---|
| 跨境连接有明显波动 | 浏览器两次首个连接阶段约 5.96s、5.83s，连接建立后首页请求到首字节约 230ms、213ms；curl 独立连接样本也有波动 | 网络因素真实存在，但单个网络的样本不能代表全国用户，不能精确分摊跨境、TLS、客户端网络等各自占比 |
| 开场让整页不可操作 | `brand-entry.tsx` 原来等待会话、页面数据、首屏头像及原图，加载后再播放 1000ms+1100ms 动画；仅 loading 阶段有 8 秒退出计时 | 线上两次页面解除遮挡分别约 15.06s、16.96s。已改为只等待路由/会话，动画 240ms+280ms，整个遮挡计时上限 1500ms。计时器仍受主线程阻塞影响 |
| 图片在当前链路传输慢 | 首屏数张约 175～225KB 正文图片，浏览器记录单张约 4.88～7.61s；头像发现后还有下一轮图片请求 | 图片继续渐进显示，不再阻挡页面导航和登录。资源响应时间包含排队、服务端及网络，未取得 Server-Timing，不能全算数据库时间 |
| 首屏下载所有管理功能 | 初始构建只有一个约 502.15KB JS 和 331.32KB CSS | 管理、统计、成员、注册管理、入网、招聘页面按需加载；当前主包约 438.21KB JS、302.12KB CSS，gzip 分别约 142.93KB、49.58KB |
| 静态资源每次需要重新验证 | 原 Caddy 全局 `Cache-Control: no-cache`；这允许存储，但通常仍需验证，并不是每次必然全量下载 | `/assets/` 内容哈希资源改为一年 immutable；其他路径继续验证，不给私人内容加公开缓存 |
| 一个消息红点翻页读取全部会话 | `unread.tsx` 原每 15 秒遍历私信和群列表；私信列表还组装最后一条消息、未读数量及身份信息，群列表包含成员 | 新增 `console/messages/unread`，一次 EXISTS 摘要查询返回布尔值，保留私信接收者、有效会话、群成员和双向屏蔽规则 |
| 侧栏读取全部个人记忆 | `workspace.tsx` 挂载时调用 `loadPortrait()`，后者顺序取完所有记忆页；每页 12 条 | 侧栏只取首批画像，完整编辑器仍读取全部页。未删减用户记忆，也未改变保存范围 |
| 后台活动刷新重复读取登录会话 | SSE 的 1.5 秒合并通知及 30 秒轮询触发全局刷新，`main.tsx` 每次重新请求 session | 区分后台活动刷新与明确刷新：后台不重取 session；登录、切换、鉴权失效仍刷新 |
| 并发相同 GET 没有复用 | 共享 API 原来对每个调用独立 fetch，例如壳层和画像编辑器可以同时请求画像首页 | 仅复用同身份、同路径的在途读取；完成不缓存，写入/主动刷新清除复用入口，返回值独立克隆，避免分页追加相互污染 |
| 评论按帖子查询缺索引 | 评论只有 comment_id 主键及作者幂等键索引；动态中的评论计数和详情页按 post_id 读取 | 迁移 000134 增加 `(post_id, comment_id DESC)`，同时增加群成员 `(agent_id, group_id)`。生产版本使用 CONCURRENTLY；尚未应用到生产 |

## 服务端与其他路径

最近一小时 Core 内存最高约 607MiB、配置限额 1536MiB；搜索服务约 979～981MiB、限额 1536MiB。Core CPU 指标最高约 0.043，PostgreSQL 最高约 0.014，均未显示持续高负载。监控点可能漏掉短时尖峰；这些数据不能排除慢 SQL、锁等待或容器限流。没有读取生产 pg_stat_statements、锁等待和连接池等待数据，不能声称数据库没有问题。

已审阅动态、推荐、公开搜索、私信/群聊、画像、首屏与刷新路径。动态搜索已有 250ms 防抖；私信搜索已有 3 秒查询超时。推荐仍在 SQL 中进行文本/兴趣评分，公开搜索使用包含匹配；数据量较大时需结合实际执行计划优化，当前没有证据支持直接替换整个检索架构。

模型生成不应与普通页面查询混为一谈：今日简报在后台生成，托管助手模型请求可等待到 180 秒，工作任务超时 210 秒。等待 Agent 回复可能包含模型、队列及宿主调度；这次没有发起付费模型调用或真人消息，未测得其端到端线上延迟。

纸张纹理原文件约 2.65MB，仍是较大的可选视觉资源；本次没有替换该图像。正文图片也仍通过业务 API 读取并校验可见范围。后续图片缩略图/对象存储方案必须保留撤回公开、访问权限和头像更新语义，不能直接把私人图片长时间公开缓存。
