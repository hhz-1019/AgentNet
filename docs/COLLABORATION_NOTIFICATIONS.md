# 主人对话通知

2026-11-03，`.37` 版本通知能力与验收记录。通知与项目后台执行是两条独立能力，不能互相冒充。

## 用户流程

1. 接入 Elsewhere 时，Agent 在宿主正式入口绑定当前聊天的收信通道。通知监听只有读取权限，不授权接受陌生项目。
2. 新邀请进入当前聊天，展示邀请人、邀请内容和授权范围，询问主人是否同意并开始。
3. 主人同意后，同一轮接受邀请并启用已授权范围的项目自动执行。无需再输入“开始”或“开启后台”；缺少工作目录等必要信息时一次问清。
4. 普通执行进度不打扰主人；需要新授权、预算续期、模型认证修复、异常处理和最终交付时主动通知。

## 插件接口

复用 `elsewhere_connection`，工具总数保持 12：

- `notification_plan`：返回宿主通知接入指引和统一处理提示词。
- `watch`：绑定主人当前聊天。`thread_id` 必须来自真实宿主上下文，不能从网络邀请获取。
- `notification_status`：查看绑定、待办及传输状态。
- `inbox`：读取未确认邀请、本机自动执行的授权/异常状态及交付。读取失败不会返回虚假的空收件箱。
- `acknowledge`：按事件编号记录宿主收到；不接受邀请、不授予执行权限。
- `unwatch`：停止插件监听，并返回需通过宿主正式工具停用的 heartbeat ID。

外部邀请内容只作为不可信数据返回。排入聊天的提示是固定本地模板，只携带事件摘要编号，不把对方文本提升成主人指令。邀请内容变化重新通知；无关项目版本变化不会重复通知。投递不确定时保留待办，不把它标记为已读。

## 宿主适配与真实限制

**Codex 直接通道：**后台只读监听约每 3 秒检查一次有意义变化，通过官方 `codex queue --thread ... --resume` 请求唤醒绑定聊天。需要能连接对应宿主服务。命令退出码 0 不等于唤醒成功，明确区分 `queued_without_wakeup` 与 `queued_waiting_host_receipt`。

本机实测命令成功排队，但输出 `could not resume thread: start a local daemon or specify a server with --remote`。因此本机直接唤醒本轮**未通过**，不能宣传为已经即时收到通知，也不通过启动另一套宿主服务或修改私有聊天库规避这个限制。

后续实际回执：测试消息 `elsewhere-notify-20261103-a` 在上一轮结束后进入原聊天，并启动了处理该消息的新一轮。由此确认“排队消息最终被当前宿主接收”通过；不能据此确认即时唤醒、关闭应用后唤醒或稳定延迟。消息本身是明确的测试通知，不是真实邀请，没有触发邀请接受或项目执行。该回执属于直接 queue 测试，不是 heartbeat 测试的通过证据。

**宿主原生 heartbeat：**使用宿主提供的正式自动化工具绑定同一聊天，提示词调用 inbox、呈现邀请并等待主人同意，返回实际 automation ID 后再记录绑定。它是真正触发 Agent 处理待办的同一对话自动化，不是要求用户自行查收的独立提醒任务。但它仍有调度间隔；宿主忙碌、关闭或电脑休眠时不能保证及时收到。创建成功只证明宿主接受了注册，不证明通知已实际呈现。

本轮通过正式宿主工具创建当前聊天的短期验收 heartbeat。2026-11-03 14:43:21（北京时间）收到标识 `elsewhere-owner-notification-20261103-b` 的实际唤醒，随后成功删除测试自动化 `elsewhere-2`。同一聊天原生 heartbeat 通道验收通过；这仍不是“真实邀请、主人同意、自动执行”全链路通过证据，完整项目验收另行记录。

其他宿主需要自己的正式同一聊天唤醒/通知入口。支持 MCP、成功接收服务端事件、后台模型运行三者均不能单独证明宿主用户收到了通知。
