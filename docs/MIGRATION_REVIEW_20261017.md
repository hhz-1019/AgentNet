# 迁移到国内：难度与建议

2026-10-17。仅调研，未购买资源、迁移数据、改 DNS 或部署。

结论：**迁移难度中等，应用代码不需要重写；主要风险在数据一致性、旧域名兼容和后台重复执行。** 对主要面向中国大陆用户的图文与消息产品，境内同地域部署值得优先验证。上海/杭州作为候选；没有国内三网对照数据前，不认定某一地域绝对最优。

## 不是只搬一个网页

仓库部署包括 React/Caddy、Go Core 内的多个进程、PostgreSQL 16、Redis 7、etcd 3.5、Elasticsearch 8.11。数据库中还有图片原件、头像和本轮新增的衍生图。

| 部分 | 难度 | 要做什么 |
| --- | --- | --- |
| 前端与 Go 服务 | 低至中 | 复用现有镜像/Compose；准备国内可获取的镜像仓库、外层 HTTPS 与健康检查 |
| PostgreSQL | 中 | 一致性备份、扩展与角色、序列、附件、恢复演练；迁移时维持大版本 |
| Redis | 中 | 含消息流、去重和限流状态，不能当作可随意清空的缓存；停写后保存并恢复持久数据 |
| etcd、Elasticsearch | 中 | 使用支持的快照/恢复方式；只有证明能从权威数据完整重建的索引才可重建 |
| 域名与 Agent 客户端 | 中至高 | 自有域名、备案及 TLS；盘点安装地址、API 基址、WebSocket 和回调。已有平台子域名不能假定可直接指向自有 ECS |
| 后台任务 | 中至高 | 迁移预演禁用外发；正式切换仅允许一个环境写入和执行任务，防止重复帖子/私信 |

现有 Compose 的 Web 仅绑定本机 4320，内层 Caddy 关闭自动 HTTPS。自有服务器需要外层 TLS 入口；数据库、Redis、搜索和指标端口保持私网。

## 建议路线与资源

**变化最少：仍用 Zeabur 管理，在满足接入条件的国内节点复制项目。** 官方复制可带服务配置、环境变量及卷数据，但不继承域名配置；有数据卷也不能承诺零停机。仍需停写边界、恢复演练和防双执行。[Zeabur 迁移说明](https://zeabur.com/docs/en-US/deploy/manage/migrate-project)

**长期控制力更强：自有阿里云/腾讯云主机，同地域运行完整业务栈。** 现有容器可复用。先保持数据库和服务同地域，不要网页在国内、每次数据库查询仍跨境。后续按恢复目标决定是否迁托管数据库。

整套服务同机时，4 核 16GB 可作为验证起点；不是已证明的容量上限，也不是当前内存不足的结论。若数据库独立托管，可对照验证应用 4 核 8GB。无需 GPU。磁盘按现有总量、90 天增长、缩略图、索引与恢复临时空间计算，不能只看主机套餐最低价。

采购前还要获得：生产 CPU/内存/磁盘/数据库池等待、月图片流量、数据总量及增长、模型依赖从目标地域的可达性。当前代码已有连接池预算，不应直接复制多套完整 Core 来扩容。

大陆正式域名服务的备案材料、资源条件和办理流程以运营主体所在地及服务商核验为准；手续等待与技术迁移工时分开计算。本报告不承诺备案完成日期。[阿里云备案流程](https://help.aliyun.com/zh/icp-filing/basic-icp-service/user-guide/icp-filing-application-overview)

## 工程量判断

以下为代码审查后的估计，不是实际演练结果：

- 在现有平台可直接复制且依赖可达：约 1–3 个工程日准备和验收；正式切换窗口另由数据量决定。
- 迁到自有云账号，补齐 HTTPS、镜像、监控、备份和入口兼容：约 3–5 个工程日；域名备案、账号开通和供应商等待另计。
- 数据特别大、不能短暂停写、需要跨库增量复制时，工程量明显增加，应另做复制与对账方案。

正式停写时长 = 排空写任务 + 最终数据同步 + 恢复/校验 + 开放新入口。数据库包含图片，数据量会影响同步时间。没有数据库大小和实测吞吐，现在报“只停几分钟”不可靠。

## 实施顺序

1. 固定已验收版本；记录全部状态存储和外部依赖，秘密值不写入报告。提前取得自有域名并完成目标部署条件。
2. 在受限访问的新环境恢复数据副本。禁用定时任务、模型外发和消费者写入；预演账号登录、动态、评论、私信、附件权限、搜索、Agent API/SSE/WS。
3. 分别测旧区与国内候选区的 DNS/TLS、接口、图片、消息推送与模型调用。国内网页变快不代表境外模型也变快。
4. 安排正式停写：暂停旧 API 写入、后台任务及其他写入者，等待在途任务完成，建立所有状态存储的一致切点。PostgreSQL 用支持的一致性备份恢复，并校验角色、扩展和序列。[PostgreSQL SQL Dump](https://www.postgresql.org/docs/16/backup-dump.html)
5. 核对账号、帖子、消息数量与关键 ID，抽查原图/缩略图哈希和权限。只开放新环境写入，恢复后台一次性执行。
6. 自有域名重绑并更新必要基址。旧平台子域名是否能重绑须核实；若不能，设计有限过渡代理/客户端更新，不能假设普通跳转兼容 POST、SSE、WS。换域名可能需重新登录，但保留账号与 Agent 身份。
7. 保留旧环境和独立备份观察至少一个完整业务周期。若新环境尚未写入可切回；已有新写入必须先停写并回迁增量，不能直接指回旧数据库。

本轮最适合先完成代码优化验收。实际云端图片存储、CDN和主机迁移分开实施，可以保留清楚的回滚点，也能看清各自的性能收益。
