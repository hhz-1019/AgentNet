# Elsewhere 插件协作框架设计

2026-10-31。设计已由用户批准，进入构建；实现与验证状态以 docs/COLLABORATION.md 及验收记录为准。

## 产品定义与选择

Elsewhere 是安装在现有 Agent 软件中的协作插件。每个人保留自己的 Agent、模型、工具、记忆和执行环境，通过插件加入共同项目，与他人的 Agent 分工、互相请求帮助、交付和验收。共同项目可以是软件、研究、文档或办公成果。

选择“薄插件 + 共享项目服务 + 宿主能力适配”。不选择统一托管所有 Agent 的工作台，也不选择首版即实现完全点对点联邦：前者改变用户工作入口，后者提前增加发现、权限与一致性负担。服务端集中保存项目事实，执行留在各自主人的宿主；协调角色是项目内可指派的角色，不强制永久中心 Agent。

## 用户体验

1. 在自己的 Agent 软件安装 Elsewhere，完成已有账号与 Agent 身份绑定。
2. 用户说“创建一个项目，邀请某位同事的 Agent 一起完成”。插件生成可审阅的项目目标、交付要求和邀请。
3. 接收者在自己的宿主看到邀请，选择共享资料范围、允许的操作和运行方式。加入项目不授予无限执行权。
4. Agent 提出分工；在已有授权内自动接受、执行和协作，超范围请求交给主人。任务和进度直接在宿主对话中查询。
5. Agent 发布成果；指定验收者接受或要求返工。项目完成以约定成果验收为准。

主入口始终是宿主对话。辅助网页用于首次绑定、权限管理、项目总览和成果查看，不强制用户迁移到新聊天产品。邀请、授权、任务和成果页面可由插件按需打开。

## 三个执行边界

### 插件

交付包包含 MCP 工具、简短协作 skill、宿主配置，以及宿主确实支持时才启用的提醒/后台适配。用户无需手填任务 JSON。插件将自然语言意图转换成项目操作，按任务提供必要上下文，并将宿主真实执行事件与产物回报。

插件不收集全量聊天或私有记忆，不因远程消息而提升宿主权限。来自队友的内容是外部任务数据，不能覆盖主人或系统规则。

### 本地宿主适配器

统一声明能力：工具调用、收件检查、外部任务启动、会话恢复、执行中消息注入、取消、成果访问。每项分别记录支持与实测状态。

支持后台进程的宿主可启用 owner 授权的 runner；只支持 MCP 的宿主在当前会话中检查收件箱和执行；没有推送/唤醒接口的宿主显示“待宿主上线”，不得伪装自动运行。更换模型不自动更换 Agent 身份，更换设备必须走已有恢复授权。

统一内部执行接口为 capabilities、start、resume、deliver_update、cancel、collect_artifacts。它们是适配契约，不承诺每个宿主都具备全部能力。宿主执行中无法注入消息时，缓存在下一安全检查点交付并报告延迟。

### 协作服务

在现有 Go Core 内增加项目、成员、工作项、执行尝试、成果、评审和事件。复用独立身份、Ed25519 认证、PostgreSQL、CLI/SDK/MCP 通道及通知设施。Go Core 是权限和业务状态的唯一真相源。

服务端保证路由、状态转换、去重、租约、权限和审计；Agent 承担理解、规划与实际工作。服务器不能仅凭模型说“完成”就把项目标记成功。

## 最小协作合同

| 对象 | 必要内容 |
|---|---|
| Project | 目标、成员、成果要求、验收人、状态、版本 |
| Membership | Agent、主人引用、角色、资料可见范围、可执行动作、有效期、撤销状态 |
| Task | 输入引用、预期输出、依赖、指派对象、接受状态、期限、验收者、版本 |
| Run | 任务、执行者、宿主、尝试号、租约、心跳、执行状态、成本报告 |
| Artifact | 项目、任务、提交者、类型、URI/存储引用、版本/摘要、来源、验证记录、访问范围 |
| Review | 对应成果的精确版本、接受/返工/拒绝、原因、评审者 |
| Event | 项目序号、事件 ID、主体、资源版本、时间、可见范围 |

任务状态：proposed → ready → assigned → accepted → running → submitted → accepted_result。补充分支为 declined、blocked、changes_requested、cancelled、failed；changes_requested 回到可执行状态并建立新 Run。采用 accepted_result 避免混淆“接单”和“验收通过”。

依赖只有在前置任务成果验收后解锁。提交新成果版本会使待审版本指向明确变化，旧版本批准不能自动批准新版本。协调者可以提出和分派任务，但不能绕过成员授权，不能替指定验收者批准。

任务指派是邀请承担责任；任务接受确认执行意愿；租约控制某次执行占有权；验收确认产物满足要求。这四者分开。

## 插件工具面

首版暴露少量高层工具，动作使用枚举和明确 schema：

| 工具 | 功能 |
|---|---|
| collaboration_project | 创建、读取项目及邀请成员 |
| collaboration_membership | 接受/拒绝邀请、查看或缩减自己的授权；扩大授权必须有主人批准依据 |
| collaboration_tasks | 创建/查询、指派/认领、接受/拒绝、报告阻塞、取消 |
| collaboration_context | 获取当前任务、依赖成果和获准共享的项目记录 |
| collaboration_updates | 发布任务相关发现，按游标读取更新 |
| collaboration_submit | 提交真实成果及验证说明 |
| collaboration_review | 对具体成果版本验收或返工 |

工具名称为拟议合同，不是已存在接口。工具参数不接受自报 owner 身份作为授权依据，始终从认证上下文解析。任何扩大权限的请求不能借普通 task update 实现。

## 跨 Agent 调用语义

A 需要 B 帮忙时，创建有输入、输出要求和截止条件的子任务；B 在其主人授权内接受；A 获得可追踪任务 ID。A 可继续其他工作，也可等待依赖，不使用无限阻塞 RPC。B 返回成果引用，A 根据约定评审。

转委派默认不能扩大范围：B 给 C 的权限不得超过 B 已获授权与 C 主人允许范围的交集；项目禁止转委派时必须拒绝。私信只作讨论与提醒，任务和成果是正式工作事实。

## 可靠性与权限

- 写操作携带 idempotency_key 和 expected_version；相同键不同负载拒绝，版本冲突重新读取。
- 服务端事务认领任务；执行租约附单调递增 epoch，失效 worker 的迟到更新不能覆盖新尝试。
- 租约过期标记需要恢复；有外部副作用的任务不得无条件自动重跑。执行者报告已做动作及凭据，必要时先查询外部状态。
- 消息至少一次投递，以事件 ID 去重，游标持久化；过期请求重新验证授权和任务版本后才能继续。
- 撤销授权即时阻止后续服务端读取/写入并发出取消；宿主停止须回执确认。无法追回已下载资料或撤销已发生外部操作，界面如实显示停止待确认。
- 每个成果继承项目和资源权限；禁止把私有本地路径当作队友可下载链接。由主人批准上传或使用受控引用，不向全体公开。
- 读取失败保留旧内容并标明待更新；提交失败保留成果和输入，不能显示已交付。

## 论文和开源的采用方式

| 来源 | 采用 | 不直接搬入 |
|---|---|---|
| [OpenAgents](https://github.com/openagents-org/openagents/tree/develop/packages/agent-connector) | CLI 适配、session 恢复、事件队列与停止控制的实现思路/合规可复用代码 | 完整身份与工作区后端；其 workspace API 需重新对接 |
| [A2A JS SDK](https://github.com/a2aproject/a2a-js) | 外部 Agent 的任务/状态/Artifact 协议适配，作为后续互操作入口 | 不要求所有插件宿主自己暴露公网 A2A 服务；不另建业务真相源 |
| [Beads](https://github.com/gastownhall/beads) | 依赖、ready、claim 和持久任务语义；可作独立验证工具 | 首版不引入 Dolt 替代已有 PostgreSQL |
| [AgentRadio](https://arxiv.org/html/2607.28430) | 执行中接收相关发现并修正行动；不能注入的宿主退化到检查点 | 不假设所有宿主支持后台注意，也不照搬论文增益 |
| [Agora 2026](https://arxiv.org/html/2609.18094v4) | 成果保留来源、继承关系、失败记录与验证状态 | 不要求办公成果都存 Git，不承诺群体效率必然提升 |

第一版的项目记录只需成果之间的来源关系和简短决策日志，不做复杂声誉、自动进化或智能推荐。运行协议稳定后，再增加跨项目可复用经验，且须重新确认共享范围。

## 实现落点与阶段

1. 业务核心：原生 core/ 中新增 Go 合同、迁移和鉴权；与现有路由直接集成（已吸收 f43baa9 的源码整理）。保留旧 handoff 的“已知悉”语义，用户明确转换后才创建项目任务。
2. 客户端：elsewhere/client 扩展 SDK/MCP；CLI 使用同一服务端合同。新增协作 skill 描述接单、阻塞、提交和验收，不把远端正文放进高优先级指令。
3. 两个真实宿主：首轮选择 Codex 与另一种有可验证执行接口的宿主；WorkBuddy/豆包 Work 在确认实际接口后加入能力矩阵。不得把 CLI 实测写成桌面插件已通过。
4. 辅助界面：现有 Console 增加必要项目/授权/成果视图。宿主内必须能完成主要工作，网页不是每一步必经入口。
5. A2A 网关：内部项目流程可靠后加入外部 A2A Agent，保持任务 ID/成果/权限映射一致。

## 第一版验收

场景：两位主人、两个独立 Agent 身份、两个真实宿主，共同完成一份含数据分析与文稿的交付。A 提供可分享资料并提出任务，B 接受后完成分析，A 基于分析写稿，指定验收者评审。实现不得依赖双方共享同一个私有文件目录。

必须验证：未授权成员无法读取；接单与验收分离；依赖解锁正确；执行中发现传达或明确延迟；断线恢复不重复副作用；重复认领只有一个有效执行权；撤销后停止新增访问；返工绑定成果版本；所有者能在原宿主查询状态并拿到最终成果。

成功门槛首先是端到端真实交付与权限正确，再比较人工转述次数、耗时、费用及返工率。单宿主模拟、协议测试、两个真实宿主测试分别报告。

## 设计边界

本设计批准后才能确定具体宿主适配实现与依赖版本。它不改变既有线上服务状态，不声称兼容所有软件。可扩展的宿主中立合同与每个宿主已实现的能力清单分别维护。
