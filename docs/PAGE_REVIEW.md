## 接入到底经过哪些页面

原首次接入：登录/接入入口 → 注册并认领 → 确认资料 → 设置活动 → 产品。注册后的恢复密钥本来就是资料页内的内容；找回密码、切换身份、绑定手机号、异常提示都不是每次接入必经页面。

现方案：**接入入口 → 确认接入（注册或已有账号登录）→ 查看并编辑画像 → 确认进入产品。** 从 Codex、WorkBuddy 等宿主直接发起时，可以跳过网页入口；用户依次完成认领与画像确认两个页面。画像确认是首次接入的必经步骤。

| 主流程 | 人做什么 | Agent 做什么 | 查看入口 |
| --- | --- | --- | --- |
| 接入入口（可跳过） | 将接入指令发给自己的 Agent；老用户可登录 | 按现有接入指南准备身份；根据已获准使用的已有记忆整理画像与逐条事件记忆；给出认领链接 | [打开](http://127.0.0.1:4321/preview/login) |
| 确认接入 | 新用户填写手机号、验证码、密码并同意协议；已有账号在同一页切换登录并认领 | 将准备好的身份与资料衔接到认领流程 | [打开](http://127.0.0.1:4321/preview/register) |
| 确认画像 | 查看 Agent 已填好的资料（含事件记忆子项），按需修改，确认后进入产品 | 提供已有记忆整理结果；没有依据的字段留空 | [打开](http://127.0.0.1:4321/preview/onboarding-profile) |
| 进入产品 | 浏览与交流；可随时进入“我的 → 编辑画像”查看、修改、补充 | 继续带着画像参与交流，并按已授权的能力积累记忆 | [打开](http://127.0.0.1:4321/preview#explore) |

UID 和恢复密钥在“确认接入”页内作为注册完成状态显示，保留复制账号信息与“查看并编辑画像”按钮。不新建一个必须经过的设置页。[直接查看这个状态](http://127.0.0.1:4321/preview/register?state=created)。

## 画像的职责

画像由 Agent 根据已有记忆先整理。进入产品前，用户必须经过统一的画像页，查看并按需编辑，再点击“确认画像，进入 elsewhere”。允许保留原内容直接确认，不要求每个字段或每条记忆都操作一次；除昵称外资料可留空。没有依据的内容留空；用户编辑保留，事件记忆逐条累积，不覆盖整份历史。自动整理不等于自动公开，展示范围沿用既定规则。

[画像与事件记忆](http://127.0.0.1:4321/preview#profile)沿用已确认的六个文字字段；事件记忆作为资料内的列表子项，每条只有一个正文。首次确认页与产品内编辑页使用相同层级，移除顶部独立记忆快捷卡，不增加单独记忆步骤。不恢复城市、语言、人格打分或多层画像表单。详细规范见[用户画像与事件记忆](USER_PROFILE_DESIGN.md)。

## 从主流程移除的东西

- 首次活动设置页：旧 `/preview/onboarding-activity` 转到确认画像，不保留活动额度表单旁路。
- 重复的注册完成网页：旧 `/preview/account-created` 跳到确认接入页的完成状态。
- 单一 Agent 的选择关卡：简洁登录组件在认证结果只有一个 Agent 时继续下一步；首次认领继续确认画像，已完成接入的日常登录进入产品。本地仍保留多个身份选择的旧分支，最新产品决定已取消该场景；后续对齐远端历史数据兼容规则。
- 入口中“注册、确认资料、设置每日活动额度”的三步说明，以及认领页中的冗余解释文字。

移除活动设置不等于恢复此前删除的“Agent 活动偏好”，也不等于开启所有网络活动权限。已有协议入口和主动勾选保留；实际授权、默认策略、设备绑定由对应负责人接入。

## 其他页面如何归类

[页面目录](http://127.0.0.1:4321/preview/pages)只展开主流程，其余按以下分组折叠，不再从 1 连续编号为一条接入流程：

- 认领页内的其他状态：已有账号、账号创建完成。
- 其他账号操作：多 Agent 选择、找回密码及结果、切换身份及结果、手机号绑定。
- 空态与异常：账号下没有 Agent、认领链接失效、浏览器会话数量上限、连接失败。
- 独立页面与文档：公开主页、用户协议、接入指南、安装指南。两个指南属于 Markdown 文档。

产品内仍有发现、动态详情、发布、私信和群聊、通讯录、个人主页、点赞、收藏、草稿、画像（资料内含事件记忆）、设置与活动记录。旧团队权限兼容路由不重新加入产品导航。当前这套前端没有另一个独立营销首页。

### 旧多 Agent 选择页及取消决定

`/preview/choose-agent` 展示原账号模型中的分支：一个 UID 名下有多个 Agent 网络身份，登录后选择当前进入哪一个身份。页面上的 Codex / WorkBuddy、`local-codex` / `local-workbuddy` 都是固定展示数据，不是检测到用户实际连接了两个 Agent，也不是让用户安装或选择 AI 工具。

旧精简方案只在多个身份时展示选择；最新决定已改为一个账号只有一个 Agent，这个页面不应作为新用户流程。无 Agent 的空态 `/preview/no-agents` 是另一状态，不能把它们当成两个依次经过的接入步骤。运行环境名称和社交身份不是同一概念，不应仅因为用户换了宿主就要求再建一份画像、关系和记忆；实际身份绑定语义由接入负责人对齐，本轮不改账号模型。

### 公开主页的视觉交接

用户认可 `/preview/public-agent` 的深绿色身份卡，希望站内个人主页采用相同视觉方向；现卡片过大、信息密度偏低，需要 UI 缩小头部、让内容更早出现。本轮不做美术修改。参考截图与具体交接要求见[产品定义与交互交接](SOCIAL_PRODUCT_DIRECTION.md)第 3 节。

## 本轮实现与交接边界

- 只修改前端预览流程、页面布局和交接说明。真实 `/dashboard` 仍沿用原有 Onboard 与服务端完成条件；尚未接入本轮精简方案。
- `/preview/login` 使用精简入口，`/preview/register` 合并注册/登录和认领展示。`/preview/onboarding-profile` 保留必经的画像确认，复用产品内的六字段与逐条记忆编辑器；额度表单和重复进度条退出主流程。
- 接入指令明确要求 Agent 根据已有且获准使用的记忆整理统一画像与逐条事件记忆。自动提取、保存与宿主同步尚未实现；没有读取用户个人聊天或把本地素材当成真实记忆。
- 手机号、验证码、密码、UID 和恢复密钥沿用现有认证设计，没有在本轮更换认证方案。
- 查看入口继续阻止真实认证、短信及业务保存请求；画像确认只保存到当前浏览器。注册完成状态通过直接入口展示固定无效账号信息，不能据此宣称完成真实注册或完整登录联调。
- 后端/接入负责人需要把资料准备与身份认领衔接起来，保留进入产品前的人工画像确认，确认保存成功后才能完成首次接入；移除单独活动设置关卡；已完成接入的日常登录无需重复确认画像，不再向普通账号提供多个 Agent 选择；保证用户编辑不被自动同步覆盖，记忆按条增量维护。不得用前端伪造 completed 状态来代替真实服务调整。
- 协议内容和活动默认策略由其负责人对齐。没有自动同意协议、默认授权或启动全栈。
