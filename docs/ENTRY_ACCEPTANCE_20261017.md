# 入场动画修复与验收

本轮仅本地修改、构建和浏览器验收，未提交或部署。

## 根因与处理

上一版把预测时间作为变形触发条件，但百分比只在 loading 阶段更新；进入 morph 后数字冻结在 66%。同时 reveal 可以在实际就绪之前跑完，页面就绪时直接撤罩。这解释了“66% 直接进入”和结尾突兀的问题。原测试只约束总耗时，没有检查实际绘出的数字和动画阶段，验收不充分。

现在以一个完成条件连接资源和视觉：首屏数据与可见图片准备完成，数字平滑到准确的 100%，完整显示至少约 180ms，再揭示页面。变形仍可与加载重叠；数字在变形期间继续更新。变形从实际填充宽度开始，避免半截进度条突然变成满宽形状。最终 logo 路径复用，减少逐帧重复构造。

首屏图片和头像共用的 ProgressiveImage 已接入准备状态，等待可见图片解码；屏幕外预取不会阻塞进入。失败图片采用原有局部替代显示。失败或超时淡出入场层并恢复页面，不能冒充成功显示 100%；已就绪的正常揭示不被原来的 8 秒超时截断。

加载 3 秒与完整揭示不能靠预测保证恰好同时结束。本轮以连贯和真实完成为先：3 秒数据加载约 4.5 秒进入；5 秒加载约 6.7 秒进入（该例含手机视口与 4 倍 CPU 降速）。此前约 0.3 秒的额外等待是旧实现的计时，已被本轮结果取代。

## 验收方式与结果

`npm run test:entry` 先构建生产文件，再以隔离浏览器运行真实前端、拦截测试接口。录制每个场景的视频，并记录 Canvas 实际绘出的百分比、阶段、时刻和绘制调用耗时，不仅观察组件状态或测试纯函数。

| 场景 | 检查点 |
| --- | --- |
| 100ms 快速数据 | 数字不跳过完成，变形和揭示完整 |
| 3 秒数据 | 先有 100% 可见帧，停留后才揭示 |
| 5 秒数据、390px 手机、4 倍 CPU 降速 | 不提前露出页面，数字单调，完整揭示 |
| 7.4 秒才返回 | 接近超时也不截断正在完成的揭示 |
| 数据很快、图片延迟 3 秒 | 图片返回与解码之前不显示 100% |
| 动画中改变窗口 | 百分比不倒退，几何重新适配 |
| 接口失败 | 无假的 100% 和成功揭示，解除遮挡与滚动锁 |
| 一直无响应 | 到等待上限退出，页面不永久锁住 |
| 主动跳过 | 解除交互与滚动锁 |
| 减少动态效果 | 不强制播放动画 |

10 种场景已通过生产构建浏览器验收。正常慢加载场景中，100% 可见约 184–187ms 后进入揭示，揭示没有被截短。绘制调用 P95 在本机普通场景约 0.1–0.2ms，手机视口与 CPU 降速场景约 0.4ms；这只测主线程绘制调用，不能等同真实手机的 GPU 帧率保证。

13 项性能单元测试、类型检查和生产构建通过。几何测试检查部分进度开始变形、轮廓无交叉、揭示覆盖视口；浏览器另外检查异常场景和实际像素阶段截图。

录屏、阶段截图与逐帧 JSON 保存在本地忽略提交目录 `.agentnet-audit/entry-acceptance/`，生产构建的最近一轮摘要为其中 `results.json`。测试不会连接生产 API 或执行真实 Agent 动作。

## 参考

- [NN/g：进度反馈](https://www.nngroup.com/articles/progress-indicators/)：进度用于建立对完成状态的合理预期，预测耗时不应被当作准确承诺。
- [MDN：requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)：动画按时间推进，考虑不同刷新率和后台暂停。
- [web.dev：动画性能](https://web.dev/articles/animations-and-performance)：避免不必要的逐帧工作。这里保留用户认可的 Canvas 形变，仅让异常退出使用透明度过渡。
